# HapieCoin · decision log (ADR)

One entry per decision. Newest last. Each entry: context, decision, consequences. This file is indexed by graphify together with `spec/`, `GAPS.md` and the mock sources so every agent can find why things are the way they are.

## ADR-001 · Product name and reference (2026-09-07)
- Context: the product being built is the user's own site; coingreeks.com is only the reference/competitor that was cloned for parity.
- Decision: the product is **HapieCoin** (hapiecoin.com). The v1 clone keeps the CoinGreeks name deliberately as the reference copy; everything else uses HapieCoin.
- Consequences: package scope `@hapiecoin/*`, all copy and artifacts use HapieCoin.

## ADR-002 · Two mocks kept side by side (2026-09-06)
- Context: user wants to compare the faithful clone with the improved version and be able to fall back.
- Decision: `mockup-clone` (v1, faithful) and `mockup-v2` (improved, Obsidian Desk design) are separate builds with separate URLs; neither is edited to become the other.
- Consequences: v1 answers "what did the original do"; v2 answers "what should HapieCoin look and feel like".

## ADR-003 · Design system: Obsidian Desk, dark-first (2026-09-06)
- Context: three directions were built (Obsidian Desk, Quant Paper, Mission Control); research on options tools favoured a dark instrument with amber "market is here" accent.
- Decision: Obsidian Desk tokens app-wide; light theme is a first-class variant; amber only for spot/ATM/primary action; green/red only for P&L and side.
- Consequences: tokens live in one file; switching to Quant Paper later is a token change, not a redesign. Launch default theme may flip to light if usability sessions show daytime retail users.

## ADR-004 · Stack (2026-09-04, confirmed 2026-09-07)
- Decision: pnpm + Turborepo monorepo; Next.js 16 / React 19 / TypeScript / Tailwind v4 / shadcn; TanStack Query + Zustand + TanStack Table/Virtual; uPlot canvas charts; shared pricing package (Black-76) in a Web Worker; Hono API on Node 22 with Zod + OpenAPI + Drizzle; dedicated market-data gateway on uWebSockets.js; PostgreSQL 17 + TimescaleDB; Redis 7; BullMQ; Better Auth; Razorpay; Docker behind Cloudflare.
- Alternatives considered: Vite SPA + Astro marketing site (acceptable if the team prefers no server components); Bun (rejected for a system that places real orders); microservices beyond web/API/gateway (rejected, adds latency and ops cost).

## ADR-005 · Monorepo with independently deployable apps (2026-09-07)
- Decision: one repository; apps/web, apps/api, apps/gateway, apps/workers; packages/pricing, schema, venues, ui, config.
- Consequences: one PR changes pricing + API + UI atomically; shared Zod schemas prevent contract drift; one CI with budgets. Split only if a separate team owns a product on its own cadence.

## ADR-006 · Chain driven by the exchange instrument list (2026-09-07)
- Context: review found v2 showed only fixed-step strikes; real Delta expiries have irregular ladders (200/400/600 daily, 500/1000 weekly, 1000 monthly; 27–52 strikes).
- Decision: strikes always come from the venue's instrument list per expiry; never from a step constant. Calls and puts render as one table with a fixed centre strike column so vertical and horizontal scroll are shared.
- Consequences: first acceptance tests of Phase 2 (see GAPS.md #1, #2).

## ADR-011 · Toolchain pins for Phase 1 (2026-09-07)
- Context: `pnpm add` resolved TypeScript 7.0.2, which typescript-eslint 8.69 rejects (`>=4.8.4 <6.1.0`); the shared tsconfig extended the repo root by a relative path that breaks through pnpm symlinks; ESLint 10 removed the `unix`/`compact` formatters the post-edit hook used.

## ADR-012 · Pricing model matches Delta India marks (2026-09-07)
- Context: `packages/pricing` was validated against 307 live Delta tickers (all BTC expiries).
- Decision: options are priced with Black-76 on `spot_price` with zero rate and no futures basis (the forward implied by every mark equals spot within 0.007 %); Greek units follow Delta: vega per 1 vol point, theta per calendar day; settlement 12:00 UTC for BTC/ETH and 16:00 UTC for XAUT, always taken from the instrument's `settlementTime`; POP uses the unshifted ATM IV; time is a 365-day year.
- Consequences: marks reproduce to 3.3e-11 USD at the implied forward; residuals in the fixture (max 3.4 USD) come from mixed spot snapshots, not the model. Unit tests assert price ≤ max(1.5 %, 0.5 USD), IV ≤ 0.005 where vega ≥ 10, delta ≤ 0.02, gamma ≤ 10 %, vega ≤ 5 %, theta ≤ 10 % (T ≥ 1 day).

- Context: Docker Desktop and WSL 2.7.13 were installed on 07 Sep 2026 but need a Windows restart; Phase 1 must not block on it.

## ADR-014 · Market-data protocol and venue adapters (2026-09-07)
- Context: Delta labels `v2/ticker` on `socket.india.delta.exchange` as legacy and offers a compact `ticker` channel on `public-socket.india.delta.exchange`; both answered live on 07 Sep 2026. The venues package and the schema package chose different field names for Instrument/Quote.
- Decision: the venues client defaults to `v2/ticker` and parses both frame formats, so the migration is a config change; the gateway speaks `@hapiecoin/schema` messages (JSON frames in Phase 1, encoder kept pluggable for msgpack later) and converts venue shapes through `packages/venues/src/schema-adapter.ts`, which is the only place the two vocabularies meet.
- Consequences: chain strikes always originate from the instrument list (ADR-006) and are validated by `ChainSnapshot.parse` before leaving the gateway.

## ADR-015 · API security and account conventions in apps/api (2026-09-07)
- Context: Phase 1 `apps/api` (Hono, Better Auth, Drizzle) had to fix several details the spec leaves open.
- Decisions:
  - Exchange credentials: API key and secret are sealed separately with AES-256-GCM, each record carrying its own IV and auth tag (columns `api_key_iv/tag`, `api_secret_iv/tag`) because GCM must never reuse an IV under one key; only `api_key_masked` is ever serialised (`BrokerCredentialPublic` is strict).
  - Referral codes are `REF` + 7 RFC 4648 base32 characters (10 chars, no underscore) so they satisfy the shared `ReferralCode` schema (`^[A-Z0-9]{6,12}$`) and survive being typed from a screenshot; the inviter's code is accepted as `ref` at sign-up and stored in `users.referred_by` only when it matches an existing user.
  - Better Auth is mounted at `/v1/auth/*`; sign-up is email + password with mandatory OTP verification (`/email-otp/verify-email` signs the user in), OTP sign-in and OTP password reset use the `emailOTP` plugin (6 digits, 10 minutes); `role` is server-assigned (`input: false`).
  - Delta credential failures map to the SCREAMING_SNAKE envelope codes required by `ApiError` (`INVALID_API_KEY`, `IP_NOT_WHITELISTED_FOR_API_KEY`, 400) with the venue's original code in `details.deltaCode`; an unreachable venue is 502 `DELTA_UNAVAILABLE`.
  - Rate limits: 300 req/min per IP globally, 5 OTP sends / 15 min per email and per IP, 10 failed verifications / 15 min lock the email; counters live in one `RateStore` (memory, or Redis sorted sets when `REDIS_URL` is set) shared with Better Auth's `rateLimit.customStorage`.
  - `audit_log` is append-only at the database level (rules discard UPDATE/DELETE) and every snapshot passes through the log scrubber.
- Consequences: the web app must send `ref` (not `referralCode`) at sign-up and read `apiKeyMasked`; rotating `CREDENTIALS_ENC_KEY` requires re-sealing rows (no key-versioning yet, see GAPS #10).

## ADR-016 · Gateway transport: `ws` now, uWebSockets.js when a compatible build exists (2026-09-07)
- Context: ADR-004 named uWebSockets.js for `apps/gateway`. `uNetworking/uWebSockets.js#v20.51.0` installs from GitHub but ships prebuilt binaries for Node ABIs 108/115/127/131 only; the repo toolchain is Node 24 (ABI 137) and the loader refuses ("supports only Node.js versions 18, 20, 22 and 23"). uWS.js also requires glibc while the gateway image is `node:24-alpine` (musl).
- Decision: the gateway runs on the `ws` package behind a transport interface (`apps/gateway/src/transport/types.ts`: `SocketServerFactory`, `Connection` with `bufferedAmount()` for backpressure). Server logic, origin check, snapshot/delta protocol, coalescing, backpressure and shutdown are transport-agnostic and tested through a fake transport; the `ws` transport has its own socket-level tests. Frames are JSON text; the encoder is pluggable (`src/encoder.ts`) so msgpack can be negotiated per connection later without touching the schema.
- Consequences: revisit when uWS.js publishes ABI 137 binaries and the image moves to a glibc base (or the gateway is pinned to Node 22 in its own image); the swap is one `SocketServerFactory` implementation. Redis fan-out (`RedisPubSub`) assumes a single feed process per Redis until a feed-leader election exists (Phase 2).

## ADR-017 · Web app boundaries: same-origin API, client boundary for the design system, nonce CSP (2026-09-07)
- Context: `apps/web` (Next.js 16 App Router) talks to `apps/api` (Better Auth cookies, `/v1`) and `apps/gateway` (WebSocket). `@hapiecoin/ui` ships no `"use client"` directives and creates React contexts at import time, which server components reject. The brief asks for a nonce CSP and a 350 KB gzipped first-load budget on `/analyse`.
- Decisions:
  - Same-origin API: `next.config.ts` rewrites `/api/auth/*` and `/v1/*` to `API_URL`, so the Better Auth session cookie is first-party and the browser needs no CORS; server components forward the cookie to `/v1/me` for the protected-route check (`src/lib/auth/server.ts`).
  - Design system through one client boundary: server components import UI parts from `src/components/ui.ts` (`"use client"` re-exports); the root layout duplicates `themeInitScript("hapiecoin.theme", "dark")` as a string pinned by a unit test instead of importing the package.
  - CSP with a per-request nonce from `src/proxy.ts` (`script-src 'self' 'nonce-…' 'strict-dynamic'`, `frame-ancestors 'none'`); every route is therefore server-rendered on demand. `style-src 'unsafe-inline'` stays because Tailwind/Radix set inline styles; documented in `next.config.ts`.
  - Budget: the workspace (chain, virtualiser) and the settings dialogs load through `next/dynamic` after first paint; `scripts/check-budget.mjs` reads Turbopack's per-route client-reference manifest and fails above 350 KB gzipped (measured 326.7 KB on 07 Sep; the `nomodule` polyfill is reported separately, as Next does).
  - Phase 1 Delta sign-in (`/auth/delta`) shows the spinner, then explains that Delta login arrives with live trading and links back, rather than faking a login.
- Consequences: adding `"use client"` to `@hapiecoin/ui` entry points would remove the boundary file (GAPS #18). The app codes against the contracts that landed on 07 Sep in `apps/api/src/routes/*` and `apps/gateway/src/server.ts` (plan `state`, PATCH updates, `{ items }` credentials, `feed.expiries`); the mock API and fake gateway under `apps/web/test/` mirror them.

## ADR-018 · Auth mount path and browser access to gateway health (2026-09-07)
- Context: the first real web→api→gateway run failed on sign-up: the browser posted to `/api/auth/*` on the web origin while `apps/api` mounts Better Auth at `/v1/auth/*`; and the browser could not read the gateway's `/healthz` (no CORS), so the expiry list fell back to the env default.
- Decision: the browser always talks to its own origin (`/api/auth/*`, `/v1/*`) so the session cookie stays first-party; Next.js rewrites `/api/auth/:path*` → `${API_URL}/v1/auth/:path*` and `/v1/:path*` → `${API_URL}/v1/:path*`. The web test mock serves both prefixes so unit tests (direct) and e2e (through the rewrite) agree. The gateway answers CORS (`access-control-allow-origin` = the allowed web origin, `vary: origin`, OPTIONS 204) on its HTTP endpoints only for origins that pass the same check as the WebSocket upgrade.
- Consequences: one auth base path on the API (`/v1/auth`); any client other than the web app must use it directly. A real integration run is part of the Phase 1 exit gate from now on, because the unit/e2e mirrors could not catch this class of mismatch.

## ADR-019 · Client IP trust and the public auth origin (2026-09-07)
- Context: the Phase 1 review (GAPS #23–#27) found four defaults that were safe on a laptop and wrong in production: the client IP for rate limits was read from proxy headers anyone can set (or fell back to one shared "unknown" bucket), `BETTER_AUTH_URL` defaulted to the API origin so the Google OAuth callback set the session cookie where the web app never reads it, production could boot on in-memory PGlite or with the OTP-logging mailer, and the web referral input used a format the API never issues.
- Decisions:
  - Client IP = the socket peer address (`@hono/node-server` conninfo). Forwarded headers (`cf-connecting-ip`, `x-forwarded-for`, `x-real-ip`) are honoured only when the peer is listed in `TRUSTED_PROXY_IPS` (`*` trusts every peer, for local development and the test harness only). Better Auth's own limiter reads a single internal header, `x-hapiecoin-client-ip`, that the app sets after that check and strips from incoming requests.
  - `BETTER_AUTH_URL` defaults to `WEB_URL`: auth URLs are public URLs on the web origin, and the `/v1/:path*` rewrite carries the OAuth callback to the API, so the session cookie is first-party (extends ADR-018). Set it explicitly only when the API is exposed on its own public host.
  - Production (`NODE_ENV=production`) requires `DATABASE_URL` and `RESEND_API_KEY` next to the existing secrets and warns without `REDIS_URL`; `createMailer` refuses the capture mailer in production regardless of config.
  - Referral input is validated with the shared `ReferralCode` schema (`REF` + 7 base32, case-insensitive on entry); no client-side format of its own.
  - The gateway re-watches every held chain topic after each instrument refresh so strikes listed intraday receive quotes (the venue socket deduplicates subscriptions).
- Consequences: deployments behind Cloudflare or a load balancer must list the proxy's address (or use the platform's own client-IP header via a trusted hop) or every user shares the proxy's bucket, which is the safe failure. Local development keeps working through `env.example` (`TRUSTED_PROXY_IPS=127.0.0.1,::1`). Google sign-in has an end-to-end test against the mock provider; the real provider still needs the client id and secret.

## ADR-020 · Chain layout mechanics: one virtualiser, three aligned row lists, mirrored horizontal offset (2026-09-07)
- Context: GAPS #1 and #2 (every venue strike; calls and puts as one table with a fixed centre strike column and shared scrolling) are the first Phase 2 acceptance tests. A single wide grid cannot give the two sides independent-but-mirrored horizontal scroll, and two separate scrollers cannot share one vertical scroll without drift. Design pass: docs/design/options-chain.md.
- Decisions:
  - One vertical scroller (`data-testid=chain-scroll`) runs one TanStack virtualiser; each virtual row is rendered three times, into the calls track, the fixed 92 px strike column and the puts track, all positioned from the same `start`/`size`, so the rows can never misalign.
  - Horizontal position is one number, `inner` (distance scrolled away from the strike column). The calls track is translated by `max − inner`, the puts track by `inner`; the header parts use the same values, so a scroll on one side moves the other by the mirrored amount and a resize keeps the columns nearest the strike in view. Wheel (and Shift+wheel) on either track, ← / → keys, and two detached scrollbars in the footer drive it; the tracks themselves are `overflow: hidden` and use `translateX`, so nothing re-lays out per tick.
  - The header lives outside the vertical scroller (two rows: side bands with their basis, then column labels) and is therefore always pinned; columns are fixed at 68 px so the header and body share one measure.
  - The range control (±6 / ±12 / all, persisted as `chainRange`) slices the gateway snapshot around the ATM index; it never generates rows (ADR-006). The footer shows "n of N strikes", Σ call OI, Σ put OI and PCR from the visible rows.
  - Below 560 px the table shows one side at a time (calls | puts toggle) with the strike column pinned at the inner edge; the same virtualiser and offset model apply.
  - Keyboard inside the grid: J / K / ↑ / ↓ move the highlighted strike, Home / End jump, A recentres on ATM, E / Shift+E step the expiry, ← / → shift columns; the palette exposes "Chain: recentre on ATM" and "Chain: show all strikes". These keys match the v2 mock's shortcut list; B / S (legs) arrive with item 3.
- Consequences: optional columns (HC-WS-021) only change `CALL_COLUMNS` and the track width; hover controls (HC-WS-023) and leg pills (HC-WS-027) attach to the existing row parts. The stale state dims the whole table and shows "as of" in the footer; the ATM band remains the only amber element (ADR-003).

## ADR-021 · Chain column layout: order from the strike outward, persisted and normalised (2026-09-07)
- Context: HC-WS-010..014, 021 and 073 add optional columns and a Column Settings dialog to the item 1 layout (ADR-020). The mock keeps one ordered list and mirrors it; the gateway quote carries prices, IVs, OI, volume, sizes, Greeks, last and 24 h change but no candle fields.
- Decisions:
  - One persisted layout `{ v: 2, order, visible }` (`chainColumns` in the UI store). `order` is read from the strike outward: the first visible column touches the strike on the puts side and the same list is mirrored on the calls side. Every read goes through `normaliseLayout`, which drops unknown ids, appends new ones in default order and falls back to the default for other versions, so a stored layout never breaks a newer build.
  - Column definitions (id, label, header, group, unit title, fixed width) live in one file; the track width, header labels and body cells all derive from the visible list, so adding a column is one entry plus one cell renderer. Essentials = Ask · Mark · Bid · OI · Δ; the Greek trio Γ Θ ν toggles together (palette and dialog).
  - The dialog applies every change immediately (no Save) and persists through the store; reorder offers ▲ ▼ buttons for keyboard users and HTML5 drag as a convenience.
  - Open / High / Low are deferred (GAPS #31) and shown muted in the dialog rather than as dead switches.
- Consequences: hover controls and leg pills (item 3) attach to rows, not columns, so they are unaffected by the layout; the 24 h change cell is the only new coloured figure (signed change, green/red per ADR-003).

## ADR-022 · Strategy legs from the chain: local per-asset state, added at mark (2026-09-07)
- Context: HC-WS-023..028, HC-TR-017 and HC-TR-018 need legs before the Builder tab and the Phase 3 strategy API exist. ADR-010 already fixed that legs are kept per asset and never cleared by an asset switch.
- Decisions:
  - Legs live in the web UI store as `legs: Record<Underlying, StrategyLeg[]>`, persisted in the browser and normalised on read (unknown shapes dropped). The Phase 3 API replaces the storage, not the shape: a leg is `{ id, asset, kind, side, strike, expiry, lots, price, iv?, symbol, status, createdAt }` with price and IV copied from the live quote at the moment of adding; quantities are integer lots and the underlying amount is derived for display only, at the lot size's precision.
  - The chain adds legs at the mark price with the row control (hover or keyboard highlight) or the keys B / S (calls) and Shift+B / Shift+S (puts); the lot count is one persisted setting (`chainLots`, presets 1..1000, default 10) shared by the control, the keys and the details dialog.
  - The active-leg limit is 10 per asset strategy (HC-TR-017); the control disables at the limit and the keyboard path toasts the reason. The builder's "8 legs for a new strategy" rule arrives with the Builder tab.
  - The automatic centring on load or expiry change only scrolls; only the A key, the ATM button and the palette command highlight the ATM row, so no row control appears before the trader asks for one.
  - The details dialog omits the mock's 24 h sparkline until price history exists (GAPS #32).
- Consequences: the Builder tab (item 4) reads and edits the same list; legs added here already carry everything the pricing package needs (`kind`, `side`, `strike`, `expiry`, `price`, `iv`, lots × lot size). Nothing here talks to a venue; no order can be created from this state.

## ADR-023 · Builder, templates and the analysis pane: drafts stay in the browser until Phase 3, pricing runs in a worker, margin is estimated as the worst defined loss (2026-09-08)
- Context: Phase 2 item 4 closes the workspace: Builder tab (HC-TR-001..049 Phase 2 rows), 28 templates, the Payoff / Greeks / Ladder pane (HC-WS-032..064 Phase 2 rows) and the workspace chrome (HC-WS-001..007). The strategy API, paper and live trading and the broker margin call arrive in Phase 3, so nothing here may depend on a server that does not exist yet. Design pass: docs/design/workspace-builder.md.
- Decisions:
  - Saved strategies ("drafts", `drafts` in the UI store) are local to the browser and normalised on read, exactly like legs (ADR-022). Save draft / Update, Load, Archive / Restore and Delete work on that list; "Save & trade" saves the draft and says that paper / live trading arrives in Phase 3. The Phase 3 API replaces the storage, not the shape (`{ id, name, asset, status, templateName, legs, createdAt, updatedAt, archivedAt? }`), and "Refresh strategies" (HC-TR-043) and "Activate" (HC-TR-046) arrive with it.
  - Every figure in the Builder ticket and the pane comes from `@hapiecoin/pricing` (`analyze`, Black-76 on spot with r = 0, settlement 12:00 UTC for BTC / ETH and 16:00 UTC for XAUT). The engine runs in a Web Worker (`lib/pricing/worker.ts`) behind the package's `PricingClient`; requests are batched per animation frame and re-issued on a 30 s clock so time-to-expiry moves without re-pricing on every tick; the inline transport is the fallback (SSR, tests, no `Worker`). Pricing legs are `lots × lot size` units at the live mark in "Live prices" mode or the stored price in "Custom prices" mode; IV is the live mark IV, falling back to the IV copied when the leg was added, then 50 %.
  - Templates are placed on the venue ladder: strike offsets `k` are row offsets from the ATM index of the chosen expiry's chain (ADR-006), never a fixed step; a template that would leave the listed strikes, or whose leg has no quote, is refused with the reason. Calendars use the next listed expiry.
  - "Margin est." is the worst defined loss at expiry (null for undefined risk) until the broker margin API exists; the tile says so. ROI-on-margin rows (HC-WS-050, 051, 058) wait for Phase 3.
  - Money formatting is one helper (`lib/money.ts`): USD by default; INR converts at the stored settings rate and formats with en-IN grouping. Strikes and prices per unit stay in USD (HC-WS-031). Position theta is per calendar day and vega per vol point, straight from the engine.
  - Builder table columns are Side · Instrument (strike + C/P or the perpetual symbol, expiry, days, moneyness) · Lots · IV · Price · Δ · Θ/day · delete. The mock's separate Type / Strike / Expiry / Unit columns collapse into Instrument and Lots because the venue has one unit (lots × lot size) and the two-line instrument cell reads faster; lots follow the chain presets on the stepper and accept any integer when typed. New strategies stop at 8 legs, editing an active one allows 10 (HC-TR-017).
  - The workspace split is one number (left-pane share 35–70 %, default 55 %, remembered per browser under `hapiecoin.split`); double-click or Home on the divider resets it. Below 1000 px the panes stack behind a Chain & Builder | Analysis toggle. The right tabs Scenarios, Vol and Structure show what arrives in Phase 5 instead of an empty box.
- Consequences: Phase 3 wires `drafts` and the ticket buttons to the strategy API and trading modes without touching the pane; the payoff canvas renderer (`components/analysis/payoffDraw.ts`) is a pure function of a frame, so the Phase 5 scenario matrix can reuse the scales. The only amber on the pane is the spot hairline and the ladder's spot row (ADR-003). No path here can create an order.

## ADR-024 · Phase 3 trading: strategies move server-side, paper is validated bookkeeping, live goes through the testnet first (2026-09-08)
- Context: Phase 3 turns Builder strategies into tracked positions (spec rows HC-TR-050..089, plus ADR-010 on HC-TR-078 / 089). ADR-023 kept drafts in the browser until the strategy API existed. The spec's "Trading safeguards" list is the acceptance test for anything that places a real order. Plan and design: docs/design/trading.md.
- Decisions:
  - Strategies and their legs live in the API (`strategies`, `strategy_legs`, `strategy_pnl`), owned per user, with status `draft | paper | live | archived`; the browser's local drafts are imported once on the first sign-in after this ships and then dropped from persistence.
  - Paper trading is bookkeeping: entry and exit premiums come from the client at the live mark (or the custom price), the server validates and records them, computes nothing from market data itself, and writes the audit log on every mutation. Unrealised P&L is priced on the client from the same live marks the pane uses; realised P&L is stored when a leg closes. Fees are estimates from the user's broker profile (notional × fee %, options capped at cap % of premium, plus GST).
  - Live trading (item 2) is a separate PR gated on the Delta India **testnet**: venue calls only behind mode + preview + confirm, server-side mark band (±5 %), per-user max notional and max legs, idempotency keys on every order, an account kill switch, and the audit log. Tests use the recording fake client; the live venue is never called by a test.
  - The Phase 4 plan quota (HC-TR-055) reads `subscriptions.featureLimits` and treats a missing limit as unlimited until plans exist.
- Consequences: the Builder's "Save & trade" becomes Paper Trade / Live Trade; "My templates" reads the API; the payoff pane is unchanged. Item 2 needs the user's testnet API key in the API's environment only (never in the repo or chat).

## ADR-025 · Live trading on Delta India: market orders through one executor, testnet URL by env, server-side safeguards (2026-09-08)
- Context: Phase 3 item 2 places real orders for the first time (HC-TR-023, 029, 055, 063, 070, 082..089). Trading-safety rules: only the live executor in `packages/venues` calls order endpoints; tests never touch live endpoints; idempotent, rate-limited, timed-out calls; paper and live visibly different. The user holds a Delta **demo / testnet** key (https://demo.delta.exchange, REST base https://cdn-ind.testnet.deltaex.org); production keys do not work there and vice versa.
- Decisions:
  - `DeltaTradingClient` in `packages/venues/src/delta/trading.ts` is the only code that calls `POST /v2/orders`, `DELETE /v2/orders`, `GET /v2/orders`, `GET /v2/positions/margined` and `GET /v2/wallet/balances`; it signs requests (HMAC-SHA256 over method + timestamp + path + query + body), times out at 5 s, spaces calls with a token bucket, refuses to run under `NODE_ENV=test` without an injected fetch, and resolves `product_id` from `GET /v2/products/{symbol}` (cached). The API's credential verifier reuses its signing.
  - Phase 3 places **market orders only**, sized in contracts: `size = lots × lotSize ÷ contract_value`, refused unless a whole number ≥ 1. Exits are `reduce_only` market orders on the opposite side. Limit orders and order editing are later work.
  - `DELTA_TRADING_REST_URL` (default = `DELTA_REST_URL`) is the base for every private call, including credential verification, so a testnet key connects through Settings → API Settings against the testnet while market data keeps streaming from production. The env `DELTA_API_KEY` / `DELTA_API_SECRET` are not used by the app: orders use the caller's own vault credential.
  - Safeguards enforced on the server before any order: global kill switch `TRADING_DISABLED`, per-user `users.trading_disabled`, `TRADING_MAX_LEGS` (10) and `TRADING_MAX_NOTIONAL_USD` per placement, mark band `TRADING_MARK_BAND_PCT` (5 %) between the previewed price and the venue's current mark, and an available-balance check against the worst-loss estimate when the wallet exposes the settling asset. Every placement carries an `Idempotency-Key`; a repeat with the same key returns the stored result; each order's `client_order_id` is `hc-<legId>-<attempt>` and a retry reuses the attempt id. Every action writes the audit log.
  - Order state lives in `strategy_orders` (client id, venue id, state pending | filled | failed | cancelled | closed, fill price, size, error, attempts). Market fills set the leg's entry premium from `average_fill_price`; partial fills stay `pending` until `sync` reconciles them from `GET /v2/orders/{id}`.
  - Trade All → Live (HC-TR-089, ADR-010) is a batch selector: every ticked paper strategy is previewed and placed one strategy at a time; a failure stops the batch and reports the strategy; a repeat with the same batch key reports the strategies that key already placed (matched on `strategies.order_batch_id`) and never places them again.
- Consequences: paper routes are unchanged; live routes add `/v1/strategies/{id}/live/preview`, `/place`, `/retry`, `/sync`, `/v1/strategies/live/batch` and `/v1/strategies/live/positions`; the web Live tab, Confirm Adjustment Order and the batch selector read them. Tests use the recording `FakeDeltaTradingClient`; the Playwright suite runs against the mock API only.

## ADR-038 · Market Analytics data comes from free public feeds through one ingest service; paid on-chain sources are deferred (2026-09-09)
**Context.** Phase 5's Market Analytics block (294 rows, `docs/research/market-analytics-data-sources.md`) needs derivatives, spot, index and on-chain data that Delta alone cannot supply. The user chose the hybrid direction with a zero budget: free feeds first, "coming soon" for screens that need paid providers, buy only when users ask.

## ADR-044 · Adjustment workbench: one atomic adjust batch, a separate draft slice, before/after in the analysis pane (2026-09-09)
**Context.** Adjusting a running strategy went through the modal chain picker with no combined preview; paper legs were added blind and live legs had no margin preview (`preview={null}`), no mark band and no idempotency. The user asked for a workbench where the trader sees the combined position before confirming, can trim, close or add to existing legs, pick other expiries, and sees the updated max loss / profit afterwards. Two clickable mockups were built and reviewed with the front-end design skill, an architecture agent and an options-terminal UX critic; the user approved layout H2 (position + ticket | chain | preview) with six extras. Design: `docs/design/adjustment-workbench.md`; mockup: `docs/design/mockups/adjustment-workbench-v2.html`.
**Decision.** (1) One atomic API batch `POST /v1/strategies/{id}/adjust` carries `adds` (new legs or add-to-existing), `changes` (`{ legId, lotsAfter }` → trim / close), `expected` marks per symbol, an `idempotencyKey` and a `reason`; paper applies it in one transaction at the client marks (adds average into the existing leg's entry), live previews then places entries and exits through the executor with the mark band, rolling the batch back on a refused check; the existing `/legs` and `/legs/:id/close` routes stay for the Details buttons. (2) The live preview accepts the proposed batch (`legs` + `exits`) so it prices what will be sent, not the open legs. (3) On the web the draft lives in its own store slice (`adjust`), never in Builder legs (ADR-026 holds); the analysis hook computes before (open legs at entry) and after (open + draft, proposed at live mark) and the pane renders after with the before curve dashed. (4) Netting is client-side and explicit: opposite side on a held contract trims or closes, same side adds; the 10-leg cap counts after netting. (5) Bounds are analytical (net call / put exposure) and valuation supports several expiries at one date. (6) The live confirm is different by design: red frame, order type, per-leg band in ticks, per-leg fill states, hold-to-place. (7) The reason is stored with the adjustment and surfaces in Details as history (the journal hook).
**Consequences.** Three PRs (A1 API, A2 workbench + paper, A3 live + plans / quick fixes / scenario date / alert stub). New traceability rows HC-TR-148..154. The Builder keeps its own chain picker; the workbench reuses the picker body inline.
**As built in A1 (2026-09-09).** `AdjustBody { adds, changes: [{ legId, lotsAfter, price }], expected, idempotencyKey?, reason? }` needs at least one add or change; `lotsAfter` must be at most the open lots (more lots go through `adds`, which keeps a separate leg row with its own entry price rather than averaging into the existing leg, so realised P&L per fill stays exact and the data model is unchanged); `lotsAfter` equal to the open lots is a no-op; `expected` marks must be positive. The cap of 10 open legs counts after the closes in the same batch. Live: every check runs before the first order (`preview()` takes the adds as entries and the trims / closes as reduce-only `exits`: product state and sizing for both, the per-placement leg and notional caps and the wallet read for the entries only), then exits go to the venue one by one with realised P&L booked per fill, then the adds are inserted and placed with the mark band (`expected` keyed by symbol, mapped to the inserted leg ids). A failed exit stops the batch with 502: what filled stays booked, the adds are not inserted, and the history row records `Stopped: <reason>`; the client rebuilds the rest from the strategy as it is under a new key. Paper exits at the client `price`, sequentially (no transaction: `apps/api` has no `db.transaction` precedent; the history row written first and the per-fill booking make a partial paper batch visible rather than silent). Each batch writes a `strategy_adjustments` row first (migration 0008: reason, added / trimmed / closed counts, realised P&L, batch id; `(strategy_id, batch_id)` unique) and fills in the counts at the end, so a concurrent repeat of the same key returns the strategy unchanged instead of placing twice; the key wins over the body, which is why the workbench sends a fresh key per Review. `Strategy.adjustments` returns the rows oldest first; `StrategyOrder.batchId` links each order to its batch. The live preview takes the same `adds` / `changes`; its `legs` list the exits first (`legId` of the open leg, opposite side) then the adds as `new-n`. Traceability: the seven new rows are HC-TR-148..154 (HC-TR-146/147 were already Builder rows), added through `mockup-v2/features` when A2 lands.
**As built in A2 (2026-09-09).** The engine's `analyze()` takes an optional `valuationMs`: legs settled by then are intrinsic, later legs keep their Black-76 time value; extremes and break-evens of that curve are searched on the price axis (grid plus every strike, a near-zero and a far price) while the unbounded sides stay analytical (the ray above the top strike), and POP uses the time to that instant. The workbench is a mode of `/analyse` held in a non-persisted `adjust` store slice (draft = lots after per open leg, picks, value-at expiry, started-at): the left pane swaps to position + ticket | chain, the pane source follows the strategy and `useStrategyAnalysis` prices the position *after* the change on every tab (kept lots at entry, adds at the live mark) with the *before* result for the ghost curve and the before → after strip. Netting is client-side in `lib/adjust/model.ts` (same side adds, opposite side trims then closes then flips; extra lots on a held leg become a separate add row, as the API stores them). The confirm dialog builds one `AdjustBody` per Review with a fresh idempotency key and the marks shown as `expected`; paper applies at those marks, live first runs the venue preview of the batch and A3 adds the order type, hold-to-place and per-leg fill states. Rows HC-TR-148..152 carry build evidence; 153 (plans compare) and 154 (quick fixes) stay `static` until A3. Deferred to A3 with the venue figures: the "margin after exceeds available" guard rail (the live confirm shows available and margin held but does not yet warn), hold-to-place, order type and per-leg fill states. Leaving the followed strategy (another card, ticked positions, the Builder or Chain tab) discards the draft, so the ticket and the request are always built from the same open legs.
**As built in A3 (2026-09-09).** Limit orders enter the executor for adjustment entries only: `AdjustBody.orderType` ("market" default, "limit"), `placeEntries` sends a leg as a limit at its `expected` mark (a leg without one goes at market), the venue clients take `orderType` / `limitPrice` (`limit_order` + `limit_price` on Delta; the fake rests a limit that does not cross its fill price), `strategy_orders.order_type` (migration 0009) and `StrategyOrder.orderType` record it. Exits stay market reduce-only, so a batch never stalls on an unfilled exit; a resting limit entry is a pending order the existing Sync reconciles. The live confirm shows per-leg band movement against the venue's band, the order type, a 1.2 s hold-to-place (pointer or Space / Enter held; release cancels), and after placing keeps the batch's fill states (filled @ price / resting / failed) on screen until Done → Details; a notional above the available balance is a guard rail. Plans (up to three, A / B / C) live inside the draft and are priced with the same marks and valuation rule as the working change. Quick fixes are pure generators over the open legs and the listed strikes (roll strikes up, roll out to the nearest strike of the next expiry with the higher strike on a tie, hedge with a call one strike above the highest short call or above spot), each ranked by the engine; an unbuildable fix says why. The scenario slider stores any ISO date as the valuation ("today" and the expiries stay as chips). Risk alerts are a persisted stub (`riskAlerts`, one per strategy, kept in USD) that the Alerts item arms. Rows HC-TR-153/154 are now `working`. After review: a limit price is snapped onto the product's `tick_size` toward the passive side (`roundToTick`; a buy rounds down, a sell up) and stored on the order (`limit_price`); a resting limit the venue cancels is retried by Retry as the same limit at that price (cancelled entry orders are retryable, GAPS #61 covers cancel / replace from the app); the live hold is disabled while any add's mark sits outside the band (the venue would refuse it) and the rolls place their replacements as plain picks so a spread on adjacent strikes rolls whole instead of netting into a naked short. Cost note: an open workbench prices up to three quick fixes and one row per plan next to the before / after pair, all RAF-batched in the worker.

## ADR-054 · Credential key rotation: key ids on sealed rows, a keyring of previous keys, lazy and batch re-seal (2026-09-11)
**Context.** GAPS #10: `CREDENTIALS_ENC_KEY` had no key id or rotation path, so rotating it made every stored exchange credential undecryptable until the trader reconnected. The spec asks for quarterly rotation with a KMS-held key before launch.
**Decision.** (1) Every sealed record carries `kid`, the first 8 hex characters of SHA-256(key) (non-secret); `broker_credentials.key_id` stores it (migration 0011; rows from before are `null`). (2) The vault is a keyring (`createKeyring(current, previous[])`): `seal` always uses the current key, `open` picks the key by `kid` (legacy rows try the current key, then each previous one), `isCurrent` says whether a row should be re-sealed. `CREDENTIALS_ENC_KEYS_PREVIOUS` (comma-separated base64 32-byte keys) lists the keys still allowed to open old rows; an entry equal to the current key is ignored, a malformed one refuses to start. (3) `openCredential` re-seals a row under the current key on its first live use after a rotation (one extra update, logged with the key ids, never the secrets); `pnpm db:reseal` re-seals every row in one pass and reports scanned / current / resealed / unreadable counts by row id. (4) A row whose key is in no ring stays as it is and the existing 409 "reconnect your exchange" path applies. Rotation procedure: generate a new key, set `CREDENTIALS_ENC_KEY` to it and move the old one into `CREDENTIALS_ENC_KEYS_PREVIOUS`, deploy, run `pnpm db:reseal`, then drop the old key from the previous list once the report shows no rows under it.
**Consequences.** Rotation no longer strands anyone. The key material still lives in environment variables; a KMS-held key would replace `credentialsEncKey` loading in `config.ts` without touching the vault contract. Rows written before this change open through the legacy path until their first use or the batch re-seal.

## ADR-056 · IV history: the API snapshots ATM IV, spot and option marks from the venue; IV rank, realised vol and the sparkline read from it (2026-09-11)
**Context.** GAPS #62 (IV rank HC-WS-096, realised vs implied HC-WS-097), #32 (the option details sparkline) and #31 (24 h range) all need a price / IV history nobody stored. The ingest service writes analytics snapshots to Redis only; the API already owns Postgres and a background loop (the order reconciler, ADR-029).
**Decision.** (1) The API runs the snapshotter (`iv-snapshot.ts`, every `IV_SNAPSHOT_MS`, default 5 min, 0 = off): it reads the venue's public option tickers per underlying (no key, never a private endpoint) through the schema adapter and writes `iv_snapshots` (ATM IV per listed expiry = mean of the call and put mark IV at the strike nearest the spot, with the spot and the ATM strike; `front` marks the nearest expiry with two or more days left, so the expiry-day IV collapse never enters the year's range) and `instrument_marks` (every option's mark and mark IV). Retention: 400 days of IV rows, 7 days of marks, pruned on each run (migration 0012). A failing underlying is logged and the others still land. (2) Read routes, public like the analytics snapshots: `GET /v1/market/iv?asset=` returns the daily front-expiry series (the last snapshot of each UTC day, ≤ 365 points), the current point, IV rank and percentile over the recorded days (`ivRankOf`), 30-day realised vol from the daily spot closes (`realisedVolOf`, sample stdev of log returns × √365) with the IV − RV spread, and the 24 h spot high / low; 503 until the first snapshot. `GET /v1/market/marks/{symbol}?hours=` returns one option's mark history. (3) The Vol tab replaces its two placeholders with the rank gauge (with the interpretation line) and the realised-vs-implied chart, stating how many days are recorded while the history is short; the header shows "IV rank N"; the option details dialog draws the 24 h mark / IV sparkline. (4) The daily series is *front-expiry* ATM IV, not a constant-maturity interpolation; the ADR records that as the definition of "IV rank" in HapieCoin.
**Consequences.** One REST call per underlying every five minutes; roughly 900 mark rows per run (≈ 1.8 M rows a week at 5 min, pruned). Only one API replica may run the snapshotter (set `IV_SNAPSHOT_MS=0` on the others). The rank reads "n of 365 days" for the first year. GAPS #31 stays open for the chain's OHLC columns (the 24 h range is now available from the API but not carried in the gateway quote). **Addendum (2026-09-11, stop and target rules as built, A4a).** Items shipped as HC-TR-165..168: `strategy_rules` (stop / target, typed in money or as a percentage of the credit received, the debit paid or the max loss, stored with the USD level), `PUT /v1/strategies/{id}/rules` replacing the set (fired rules stay as history), `DELETE` disarming, Reconcile disarming. A fire claims the rule (armed → fired, once across ticks and replicas), exits short legs first then longs at market through `placeExit` with three attempts and a backoff, books each fill with the close reason `stopped` / `target`, disarms the strategy's other rule, records a `rule:` batch in the history, audits `strategy.rule_fire` with marks, fills and failures, and tells the trader by mail / Telegram; a refused leg is named on the card as still open. Paper fires the same way with no orders. The kill switch holds a live fire (the rule stays armed and says why). The Protect step follows a trade from the Builder and can be switched off; the capital gate now refuses a net debit above the available balance on the server (GAPS #81).

**Addendum (2026-09-11, leg stop, spot level, time exit and re-enter as built, A4b).** Items shipped as HC-TR-169..172 on the same `strategy_rules` table (migration 0016 adds `leg_id`, a cascade reference to the leg, and `scope`). Three more kinds, each with its own triggers: `leg_stop` watches one open leg's mark (`multiple` × its entry price, priced on the server from the leg's entry when armed, or a `price`) and exits that leg alone (`scope: leg`, the default) or the whole strategy; a short leg is stopped when its mark rises to the level, a long one when it falls to it. `spot` watches the underlying (`above` / `below`, the spot taken from the first ticker of the tick that carries one; no spot, no judgement that tick). `time` fires `at` an ISO instant or at `dte` days (inclusive, fractional days counted) to the nearest settlement of the open dated legs, with the reason `squared_off`; with only a perpetual open a days rule is disarmed as void, as is a leg stop whose leg was closed by a click, the settler or another rule. The level column keeps its name (`threshold_usd`) and now holds the kind's own unit; `ruleLevel` in the schema computes it for every kind. One rule per kind, one leg stop per leg, at most twelve. Judging order is stop, leg stop, spot, time, target (`RULE_KIND_ORDER`); a leg-scope fire leaves the strategy's other rules armed unless nothing is left open. The Protect dialog gained a Leg stops block (one row per held leg with the current mark), a Spot level row and a Time exit row (the instant typed on the trader's clock, sent as an instant); the card line and Details name every kind (`ruleText`). The workbench footer carries the armed rules and a Protect button beside the alert line, so the alert (tells) and the rule (exits) sit together. Re-enter on a closed card (any close reason, while its expiry has not passed) creates a fresh draft of the legs the strategy held, at today's marks, named "<name> re-entry", and opens the trade dialog of that tab on it: the entry, the capital check and the Protect step happen there; nothing is placed by the button itself. Decided against: a re-enter that rolls expired legs to the next expiry (that is the adjustment workbench's roll), and a time rule counted to a chosen expiry rather than the nearest (one number the trader can read off the card).

## ADR-062 · Replicas: a Redis leader lease for the API jobs and the gateway feed; follower gateways serve clients from a shared registry and snapshot store (2026-09-11)
**Context.** Every background job (order reconciler, IV snapshotter with the alerts pass, Telegram linker) started in every API process, so a second replica would double-run them (GAPS #71); every gateway process opened its own venue feed and published every frame, so two gateways double-published (GAPS #16). The stack could not be restarted without downtime or scaled past one copy of each process (roadmap F26; docs/research/platform-roadmap-2026-09.md §6). The user asked for fan-out across gateways, not only standby.
**Decision.** (1) A leader lease in Redis (`SET key owner NX PX ttl`, renew and release by compare-and-set script; `leader.ts` in both apps, the memory lock for a single process) with `runAsLeader`: acquire, renew every ttl / 3, give the role up on a failed renew or a Redis error, keep retrying. (2) API: `startJobs` starts the jobs on acquire and stops them on loss; `API_JOBS_ROLE` = leader (default) / always / off; `LEADER_TTL_MS` 15 s; `/healthz` reports `jobs: { role, active }`. (3) Gateway: `RoleFeed` wraps the feed in two modes. The leader runs the venue socket and publishes; a follower loads the instrument list over REST, opens no socket and serves clients: its clients' holds go to the **held-topic registry** (one Redis hash of (topic, instance) leases, re-leased every `HOLD_SYNC_MS`) so the leader watches the union across gateways; a follower's first frame comes from the **snapshot store** (the leader writes each held chain's rows with its `seq` at most once a second while it changes, and every spot) with a short wait for a topic nobody held before, else the local REST rows at seq 0; live frames arrive through the Redis fan-out; frames that arrive while the first snapshot is fetched are queued and replayed after it. Mode changes (lease taken or lost) never touch client connections; a new leader watches its clients' topics at once and the registry's within one sync, and it **announces a snapshot frame on the fan-out for every chain it (re)watches**: its per-topic seq starts again, and the web reducer ignores frames at or below the seq it last saw, so without the announced snapshot every client would freeze after a takeover; the snapshot resets each subscriber on every gateway and the following deltas continue from it (a server drops an announced snapshot queued behind the one it is sending itself). `GATEWAY_ROLE` = auto (default) / follower; `/healthz` carries `role`, `/metrics` `hapiecoin_gateway_leader`. Without Redis the single process is the leader through the memory lock, so a one-copy deployment behaves as before.
Every lock call is bounded to ttl / 2 (a hung Redis connection counts as a lost lease, because ioredis queues commands while disconnected), and a leader whose `onAcquire` throws (the venue session did not start) gives the lease back and retries. Instance ids always carry a host:pid:random suffix, so one env file shared by several replicas cannot make them share a lock owner. The leader rewrites every held chain to the store at least every 20 s even without ticks, so a quiet expiry never expires under a follower.
**Split-brain window.** After a partition or a process pause the old leader can keep publishing until its next bounded renew fails: at most renewMs + timeoutMs (about 12 s at the 15 s default lease). Both leaders then write the snapshot store (last writer wins) and both publish frames; the announced snapshot from the new leader and the reducer's gap handling put every client on the new stream once the old one stops. Acceptable for market data; the API jobs are idempotent per pass (the reconciler re-reads venue order state), so a doubled pass costs a duplicate query, not a duplicate order.
**Consequences.** Any number of API and gateway replicas can run; exactly one runs the jobs and one the feed; takeover within the lease. GAPS #16 and #71 close. The client reducer's gap handling covers the seq change at a failover (a fresh snapshot after resubscribe). Not yet done: a two-process run against a real Redis (Docker) recorded with deployment (C13); the ingest scheduler stays one replica by convention. Tests: leader.test.ts (both apps), jobs.test.ts, coordination.test.ts, role.test.ts, fanout.test.ts (two gateways on a fake Redis: follower first snapshot, live frame through the fan-out, takeover).

## ADR-066 · Pricing: carry (r, q) and an injected trading calendar; exercise style shown, never modelled (2026-09-11)
**Context.** E20 step 3 (ADR-060 decision 2). ## ADR-067 · Deribit, data-only: a second venue behind the port, inverse contracts priced in USD at the adapter, one gateway session per venue (2026-09-11)
**Context.** ADR-060 decision 2 chose Deribit, data-only, as the second venue because its inverse BTC- and ETH-settled contracts exercise the port properly. Verified on 11 Sep 2026 against the live public API (fixtures in `spec/fixtures/deribit-*.json`) and docs.deribit.com: `public/get_instruments` (one request per second sustained), `public/get_book_summary_by_currency`, `public/ticker`, and the JSON-RPC socket with `public/subscribe` on `ticker.<name>.100ms`, server heartbeats and `test_request` frames answered with `public/test`. (2) The port's factories are typed with venue-agnostic interfaces: `VenueRest { products, tickers }` (what the API's snapshotter and rules tick read) and `VenueMarketData` (the gateway's session shape); the Delta REST loop moved to a shared retrying `JsonHttp`; `chain.ts` and the schema bridge stamp the record's own venue (`schemaVenueOf`); `VENUES` gains `deribit`, so the instrument-id and topic regexes widen by construction. (4) The API accepts Deribit exchanges and paper strategies on them, but refuses API keys and any live path for a data-only venue with a 409 that says so (`dataOnlyReason`).
**Consequences.** A Deribit chain can be served today by enabling the venue on a gateway; the client still asks for `delta_india` until 4b adds the venue switch (store, header chip, venue-keyed chain and leg-quote subscriptions), and 4c moves the API's trading client and lot defaults to the broker's / strategy's venue (GAPS #83 stays open for those two). ## ADR-068 · Accounts: several labelled exchange keys per broker; a strategy trades through one of them (2026-09-11)

**Context.** Delta Exchange India offers sub-accounts, each with its own margin balance, orders and positions (research §6; the user confirmed one on the demo account). Roadmap A5 (trade-lifecycle §2.3 C): a trader who keeps one strategy per sub-account is shielded from an exchange-level stop on a shared contract, but HapieCoin held one key per exchange, chose it by broker id everywhere, and compared every live strategy with one positions read.

**Decision.** An *account* is one connected key. `broker_credentials` gains `label` (default "Main") and the unique index becomes (user, broker, label); at most `MAX_ACCOUNTS_PER_BROKER` (5) per exchange. `strategies.account_id` names the key a strategy trades through (a nullable reference; `set null` on delete, but the route refuses the delete first). The key is resolved once, on start or place, by `openCredential(deps, user, brokerId, venue?, accountId?)`: the named account, else the broker's only key; several keys with none named is a 409, never a guess. Every path that opens a key for a strategy (place, retry, sync, exits, adjustments, close-all, the reconciler, the settler, the rules engine, the positions and positions-exit routes) passes the strategy's account. When a second key arrives for an exchange, the paper and live strategies on that exchange with no account named are stamped with the first key, the one they were placed through. `DELETE /v1/credentials/{id}` removes one key and answers 409 while a live strategy trades through it (or, from before accounts, through that exchange with no key named); an exchange id is still accepted while the exchange has a single key. Web: API Settings lists the keys with their labels and a per-row Disconnect, and proposes the next free name (Main, Sub 1, …); the trade-mode dialog shows an Account select when the chosen exchange has more than one key (the strategy's own account preselected on Go live); the Live tab makes one positions read per distinct account and compares each strategy with its own (a strategy from before accounts on an exchange with several keys shows "no account named" and is left out of the check); the wallet chip, the portfolio bar, net positions and the workbench read the account chosen last (`store.accountId`), with a select in the net-positions panel. The card and Details show the account label once an exchange has more than one key.

**Consequences.** Paper strategies record an account too, so Go live and the drift check read the right key. A trader can map one strategy to one sub-account and let the exchange net per sub-account. Not verified: whether Delta scopes an API key to the sub-account it was created under; the design does not depend on it (a key is whatever Delta scopes it to), and the API Settings copy tells the trader to switch to the sub-account before creating the key (GAPS #85). Rejected: separate HapieCoin logins per sub-account (breaks the Journal and the verified P&L later); a silent fallback to another key on delete (an exit through the wrong sub-account is worse than none). Tests: `credentials.test.ts` HC-SH-123, `trading-live.test.tsx` HC-TR-173..175, `dialogs.test.tsx`, e2e `settings.spec.ts`.

## ADR-072 · Strategy Wizard: a view, a move and a date become three defined-risk strategies priced at the live chain (2026-09-12)
**Context.** Roadmap item 8 from the competitor research: a first-time trader has a thesis ("BTC up 3 % by the 25th"), not a strategy name. The Templates tab already places every template on the venue ladder and prices it in the worker (`useTemplateStats`, ±6 % outlook), and `useTemplateLoader().load` is the one place a template becomes Builder legs; but nothing turns a thesis into a ranked shortlist, the templates carried no risk metadata (only the invariants test's shape table knew which have a bounded loss), and the Builder had two sub-tabs with a coercing tab handler. Design pass: `docs/design/strategy-wizard.md`.
**Decision.** (1) Every template names its risk: `StrategyTemplate.risk` is `"defined"` when the loss at expiry is a finite number and `"undefined"` otherwise (eight templates: the naked short call, the short synthetic and short perp, the covered put, the short straddle and strangle, the jade lizard and the call ratio spread); the invariants test asserts the field against the priced payoff for all 48, so it cannot drift. "Defined" is the mathematical bound, not a promise of a small number: a sold put or a long perpetual is defined and its worst case is shown as the figure it is; the ranking by return on risk pushes such structures to the bottom. (2) The wizard is a third Builder sub-tab, `wizard` (`BuilderSubTab`), reached from the tab bar, the Builder empty state ("Ask the wizard"), the palette command "Strategy wizard" and the shortcut `W` (registered by the workspace while mounted, listed under Analyse workspace in the ? help). Its inputs are component state: the view (Bullish, Bearish, Neutral, Volatile), an unsigned move in percent (the view gives the sign; a typed target price sets the move) and a listed expiry; the shared payoff target is written only when a card is used. (3) Candidates are the eligible templates (`risk === "defined"` and no `calendar` tag; calendars need the later chain, GAPS #76) materialised on the live chain at the chosen expiry and priced one pass per chain snapshot (`useWizardCandidates`: sequential, 81 points, the venue calendar; a pass is never abandoned, a newer chain waits for it and one more pass follows, at most one pass every two seconds, so a fast feed can neither keep the first result from landing nor flicker the cards). Every thesis figure derives from the expiry curve without repricing (`wizard.ts`): the P&L if right is the expiry payoff at the target price for a directional view, the least anywhere inside the ±move band for Neutral and the smaller of the two band edges for Volatile (`pnlAtExpiry` extends the curve as a straight line beyond the engine's range, which already reaches past the outer strike); the fit reads the same curve: a directional view fits when the structure profits at the target and more than at the opposite move (a condor that profits equally either side is a bet on the range, an OTM credit spread that profits most in its direction still counts; a bought call that cannot pay for itself at +0.5 % is not offered as bullish at +0.5 %), Neutral when it profits everywhere inside the band, Volatile when it profits at both band edges and less at spot; the rank is return on risk (`pnlThesis / |maxLoss|`) descending, then POP, then name; only fits with a positive thesis P&L are shown, at most three, each with one earned tag (best return on risk, highest POP, smallest max loss: an argmax over the shown cards, never repeated). Fewer than three fits says so ("2 of 3 fit this ladder"). (4) "Use this" writes the legs the card shows (the placement the pass priced, not a fresh one on a chain that may have moved) through the Templates loader's store writes (legs, name, Builder sub-tab, toast) and then sets the payoff target to the thesis price (the upper band edge for Volatile, spot for Neutral) and the days to the expiry, so the chart opens on the thesis. (5) Copy follows the design: every figure carries its unit and basis (the basis line names lots × lot size, marks and the expiry; "Max loss (the most you can lose)"; "If right on 25 Sep"); amber only on card 1's button; green and red only on P&L, max profit and max loss; with the feed disconnected the basis line reads "Feed disconnected · figures from HH:MM:SS"; arrow keys move between the view chips; the move field holds the typed target price at full precision and a price on the other side of spot switches the view. Not built from the design: the "updated N s ago" age on the basis line.
**Consequences.** A thesis becomes a shortlist in one pass of about 34 worker requests per chain snapshot; changing the view or the move is instant. The wizard never trades and never invents a strike (ADR-006: strikes come from `materialiseTemplate` on the listed ladder; a template that reaches past the ladder drops out). Not built (GAPS #88): a target date before the expiry (the thesis is valued at expiry only), calendar-family candidates, and the assistant's free-text thesis parsing. Placement (materialise → addLeg → toPricingLegs) is one shared helper, `placeTemplate`, used by the Templates tab and the wizard. Tests: `wizard.test.ts` (eligibility, the thesis prices and P&L, extrapolation, the fit rule, ranking and tags on the Black-76 ladder), `useWizardCandidates.test.tsx` (the pass lands under React's development double-mount, which the first CI run of the e2e caught: the scheduler lives in refs and never closes over a render; a newer chain reprices after the gap; no inputs → waiting), `templates.invariants.test.ts` (HC-TR-177: risk against the payoff for all 48), `builder.test.tsx` (HC-TR-176..178: states, units, the derived price, the band, no-fit, Use this → legs, name, target), `shell.test.tsx` (the palette command), `workspace.test.tsx` (`W`), `assistant.test.ts`; e2e `analyse.spec.ts` HC-TR-176..178 and the `analyse-wizard-{dark,light}` screenshots in `visual.spec.ts`.
## ADR-073 · Verified P&L from the exchange's fills: read per key, average cost per contract, the Journal's figure beside it (2026-09-12)

**Context.** Roadmap B7 (research §3 takeaway 2): a P&L figure that does not rest on HapieCoin's own bookkeeping, so it holds trades made on the exchange's own app and cannot be faked with a screenshot. Nothing in the repo read fills before this; the venue client had orders, positions and balances only.

**Decision.** (1) The trading client gains `listFills(creds, { after, pageSize })`, read-only, cursor-paged newest first, tolerant of the documented Delta fill shape (`id, size, price, side, product_id, product_symbol, order_id, role, commission, created_at`); an unreadable page throws like positions do, so "no fills" and "could not read fills" never look alike. (2) `venue_fills` keeps every fill per key (unique on account + venue fill id, the venue's row kept raw) and `fill_watermarks` records each account's last read, newest fill and last error; migration 0019. (3) `ingestFills` walks each account's pages newest first until it meets a fill already held; a first read stops after its page cap (3 for the job, 5 for the button) and keeps the cursor on the watermark, and later passes backfill from that cursor a few pages at a time until the venue's history ends, so nothing is skipped and the block says "older fills still being read" meanwhile. The product's contract value is looked up once per symbol at ingest, while the product is still served, and stored on the fill. After each pass the venue's net position per product is compared with what the held fills add up to; a product that disagrees (opened before the read, or beyond the venue's history) is named as partial on the account, never guessed. A leader-only job runs it every `FILLS_INGEST_MS` (5 min, 0 off); `POST /v1/verified/refresh` runs it for the caller now and skips an account read within the last 30 s. A failure is written on that account's watermark as a sentence and shown, never thrown. (4) `verifiedFromFills` in the schema package is the arithmetic, shared with the web mock: fills in time order, average cost per product, a reducing fill realises (price − average) × contracts × contract value signed for shorts, a flipping fill closes the old side and opens the rest at its price, commissions come off on their day, a product without a contract value is skipped and counted. (5) `GET /v1/verified/pnl` answers per account and in total (net of commissions, gross before them, 7 days, 30 days, commissions), the oldest fill held, the last read, and the Journal's own realised figure over live strategies closed since that oldest fill with the difference taken gross to gross, because HapieCoin books live strategies before fees and at expiry through the settler; the block says so when they differ. (6) The Journal shows the block above its stats once a key is connected: totals, fills and since, the agreement line, per-account rows with errors, and Refresh.

**Consequences.** Verified P&L covers every connected key, so a sub-account traded by hand counts too (that is the point). Disconnecting a key drops its fills; reconnecting re-reads what the venue still offers. Not yet verified against a live response: the exact fill shape, whether the cursor is `meta.after`, and that pages come newest first (if the venue paged oldest first the walk would stop after its first pass; GAPS #89 tracks all three, and the venue's rows are kept raw on every fill for the comparison). Money arithmetic uses the engine's existing float-then-round-to-cents convention (HapieCoin's P&L everywhere), not integer minor units; a mismatch of a cent against the venue's own statement is possible and is what the raw rows are for. Deferred to B7b: the public page per trader and the share buttons. Rejected: calling HapieCoin's own order fill prices "verified" (they cover only the orders HapieCoin placed).

## ADR-074 · Mindful Trading pause: a countdown before a live order on a day the trader is already down (2026-09-12)
**Context.** Roadmap item 10 from the competitor research: "a pause with the strategy's max loss, margin and the day's realised P&L before placing a live order when the trader is down on the day; cheap; fits the no-confusion bar." Every live entry (the Builder, the palette, the templates, Re-enter, Go live from a card) already converges on `TradeFlow` → `TradePreviewDialog` → the place call, and the batch on `BatchLiveDialog`; the preview already states the order's capital at risk and the exchange's margin in use. What did not exist: a day P&L the trader could be held to (the bar's Day P&L is browser-computed over paper and live together; the server has no per-day figure, GAPS #38 was closed by the browser writer), a per-user preference for it, and a place in the flow that waits. **Decision.** (1) Scope: live entries only, the single flow and the batch. Live adjustments, exits and square-offs are never paused (they reduce or repair risk); paper is never paused. (2) "Down on the day" is `liveDayPnl` (`lib/strategy/mindful.ts`): the live strategies' day P&L as the bar computes it (`dayPnl` against the last P&L point before today) plus the live trades closed today at their day share, read from the same book; the day is the UTC day the P&L points are keyed by and is written on screen as "since 05:30 IST (00:00 UTC)" so the pause and the bar's tile never disagree; the figure is unknown, and no pause is decided, while an open live leg has no price. (3) The preference lives in `UserSettings.mindful` `{ enabled, thresholdUsd, pauseSeconds }` (defaults on, "0" = any loss, 30 s; 10..300 s), a jsonb column with the same default (migration `0019` on this branch, renumbered behind the other session's 0019 when the branches meet), defaulted in the zod object so an older client's PUT keeps validating (a tab loaded before the deploy that replaces the whole object without `mindful` puts the pause back to its default: the safe direction, accepted); every settings dialog's save now completes its patch from the cached settings before the strict PUT (`useUpdateSettings`), the trap GAPS #45 recorded for the header toggle; the `MindfulDialog` is reached from the settings menu (the row shows "30 s" or "off"), the palette ("Open Mindful trading") and the bar's Day P&L tile; switching it off shows one sentence, not a confirm. (4) The pause is decided once per flow, when the live preview opens (`TradeFlow` latches `mindfulFor(settings.mindful, strategies, book)`), so a tick that lifts the day above the threshold mid-pause does not cut it short; the preview and the batch dialog then show the `MindfulPause` block (today's live P&L in red, "This order could lose" from the preview's own capital-at-risk figure, "Margin in use" from the exchange check, the basis line naming the strategies counted and the day, "Nothing is blocked: the button returns when the pause ends") and the Place / batch button is replaced in place by a disabled outline countdown until it reaches zero; there is no skip. Reopening the flow restarts it. (5) Browser-side only, and the copy says so: the server has no day P&L yet, so this is a mindfulness aid, not a control (GAPS #90 keeps server enforcement for when a server-side daily writer exists).
**Consequences.** A trader who is down on live trades sees the loss, the worst case and the margin together and waits the seconds they chose before the next live order; nothing else in the flow changes, and a good day, a paper trade or an exit never meets the block. Tests: `mindful.test.ts` (the day figure over active, closed-today, older-close and paper rows; unknown while unpriced; the pause rule and thresholds), `trading-live.test.tsx` HC-TR-182 (the block, the countdown replacing the button, the button returning, off / threshold / paper never pause, the batch), `dialogs.test.tsx` HC-TR-183 (prefill, validation, the off note, persistence, mounting through the registry), `shell.test.tsx` (the palette row), `accounts.test.ts` and `settings.test.ts` (the schema bounds, the default for an older client, the round trip, an out-of-shape row); e2e `settings.spec.ts` HC-TR-183.
## ADR-075 · The public trader page: a chosen handle, off by default, totals net of fees always, three sections opt-in, shared by intent links and a client-drawn card (2026-09-12)

**Context.** Roadmap B7b (research §3 takeaway 2): a verified figure markets itself only if a trader can show it. The figure exists since ADR-073; what leaves the server for a stranger has to be decided once, and sharing must not depend on platform keys or an image service. The user chose: a handle the trader picks, totals plus a trend with the rest opt-in, and X, Telegram, a copied link and an image card as the share targets.

**Decision.** (1) `trader_pages` (user_id PK, unique lower-case `handle`, `enabled`, `show_days`, `show_accounts`, `show_months`; migration on this branch): the page is off until the trader turns it on, and it cannot be on without a handle. `Handle` in the schema package: 3–20 letters, digits or underscores, lower-cased on input, a reserved list (route words, "hapiecoin", "admin", "delta"); a taken handle answers 409, never a silent suffix. (2) `GET /v1/public/traders/{handle}` is unauthenticated, cached `public, max-age=60`, and answers 404 alike for an unknown handle, a malformed one and a page that is off, so the response never tells a visitor whether a handle exists. Its body is `publicTraderFrom` in the schema package, the only projection that leaves the server: name, handle, all-time / 30-day / 7-day realised P&L net of fees, fill count, since, last read, a `partial` flag; days (merged across accounts), accounts (label, figure, fill count, since) and months only when the trader ticked them; never account ids, commissions, balances, positions, products, order sizes or the Journal comparison. The visitor sees USD only. (3) `/t/<handle>` is a public Next page like `/s/<code>`: the body is a client component reading the same-origin API; `generateMetadata` reads the API server-side (API_URL) so a shared link previews the 30-day figure, and falls back to a generic title when the page is off or the API is down. (4) Share: an X intent link and a Telegram share link built from the 30-day figure and the URL (the referrals precedent, no SDK), copy link through the clipboard helper, and a 1200×630 PNG card drawn on a canvas in the browser and saved through a data URL, so no image library, no server rendering and no CSP change. (5) Settings: a "Public page" dialog under Account (both header menus) with the handle, the switch (disabled until the handle is valid), the three checkboxes, the link with Open, and the share bar once the page is live; renaming warns that shared links break.

**Consequences.** Anyone with the link can read the totals; the trader accepts that by switching the page on, and can switch it off or rename the handle at any time (old links then 404). The public route recomputes the figures per request behind a 60 s cache and the global per-IP limit; a keyed limiter or a stored figure comes if a page gets popular (GAPS #91). The card's colours are fixed (dark card, amber rule, green and red figures) whatever the viewer's theme, since it is an image. Rejected: a random slug (harder to say aloud, and the user chose a handle), a display-name slug (collisions, renames), OG images rendered on the server (a library the project does not carry), a public JSON that reuses `VerifiedPnl` (it names account ids and the Journal comparison).

**Context.** Roadmap item 11 from the competitor research ("a screener on the chain data we already hold: highest IV rank, richest premium per day, widest skew"). The browser already subscribes every listed expiry's chain (the Vol tab, `useChains`, well inside the gateway's 50-topic budget), the quotes carry mark, mark IV, greeks and OI, and `atmIvOf`, `skew25`, `chainTotals`, `expectedMove` and `termShape` exist; what did not exist was a premium-per-day or per-row break-even figure, a cross-expiry table, or any sortable table inside the workspace (the analytics pages own the one sortable `DataTable`). Without spot the spot-based figures are null and say so. (3) The panel folds once per tick burst (`useChains` batches per animation frame), filters in component state (side, |Δ| band, expiry set, minimum OI), renders through the analytics `DataTable` (client sort, nulls last, column menu, CSV) sorted by premium per day, shows the top 100 with the count, and an Expiries view sorted by days. The basis line names the count, "marks", the front IV rank (1 y), spot, the term shape and whether the feed is live. (4) Buy / Sell add one Builder leg at the chain lots with the row's mark and IV, the chain panel's rule and toasts; Chain sets the workspace expiry and opens the chain tab. (5) Every column header states its unit and basis; premium per day says it is earned only by a seller whose option expires worthless; IV−ATM is named as vol points against the expiry's own ATM so it is not read as IV rank.
**Consequences.** A trader scans the whole board of an asset in one table and hands a pick to the Builder in one click, on data already in the tab (no new subscriptions beyond what the Vol tab makes; the only request is the IV history the Vol tab and the header share, for the basis line). A spot frame alone does not refold the board: spot enters the fold quantised to about 0.06 %. Not built (GAPS #92): a per-instrument IV rank (needs per-symbol history beyond the 168 h mark history and one request per symbol), plan gating of the screener (the research puts it behind the paywall; no entitlement key exists), saved filter presets. Tests: `screener.test.ts` (rows per quoted side, the per-day figures, IV−ATM, the break-even sign, the one-hour floor, settled expiries dropped, no-spot nulls, the expiry rows, the filters), `screener.test.tsx` (two expiries on the fake gateway: sort, filters, the Expiries view, Buy / Sell / Chain), `workspace.test.tsx` (the tab), `shell.test.tsx` (the palette row); e2e `analyse.spec.ts` HC-WS-110..112 (its first run is the PR's CI; the `analyse-screener-{dark,light}` screenshots in `visual.spec.ts` land on the next successful local visual run, GAPS #92).
## ADR-077 · Backtest on our own end-of-day chains: a daily per-strike table at the settlement hour, a template entered every day and held to expiry, recorded marks or a labelled model (2026-09-12)

**Context.** Roadmap item 9 (research §3 takeaway 5): Opstra's paid moat is a backtest on EOD data, and ADR-060 reserved the only data-backed claim about the 48 templates for "backtests on our own snapshots". What we record today is per-strike marks for seven days (the 5-minute stream, ADR-056) and ATM IV for 400 days; the ATM series carries no strike ladder, so a chain older than a week cannot be rebuilt from it, and skew before the record began is not recoverable at all. The pricing package already had every piece of arithmetic (Black-76, intrinsic settlement, calendars, the template placement) but the templates lived in the web app.

**Decision.** (1) `chain_eod` (venue, asset, day, expiry, strike, kind, mark, mark IV, spot, ts; unique per row; migration on this branch): the first snapshot pass at or after the asset's settlement hour (12:00 UTC, XAUT 16:00) writes that day's whole chain from the pass it already read, once a day and in one transaction (a failed batch leaves no half day for the once-a-day gate to mistake for a done one), kept 400 days (about 900 rows per venue and day; pruned by a ts index once a day, with the write). The first write for a venue and underlying backfills up to the previous week from the mark stream (the last pass at or before the settlement hour each day, symbols parsed back through the venue codec, the spot from the same pass's IV snapshot), so the tab has close to a week of history on day one; the oldest day may already be pruned when a later settlement hour (XAUT) runs the first write. (2) The template catalogue and `materialiseTemplate` move to the pricing package (the web module re-exports them typed on `Underlying`), so the API places a template exactly as the Builder, the Templates tab and the Wizard do. (3) `runBacktest` in the pricing package, pure: on every recorded day the template is placed on that day's ladder around the Builder's ATM row (the last strike at or below the spot, the gateway reducer's rule), on the nearest listed expiry with at least `minDte` days left (1 or more); each option leg settles at intrinsic value on the first recorded day on or after its expiry date (a backfilled day is stamped before the settlement hour, so the date decides; a calendar's legs settle separately), a perpetual rides to the exit day and a template made only of perpetuals is refused as unfit (nothing to hold to); a trade whose legs have not all settled by the last recorded day is "open" and marked on that day from the recorded mark of the same instrument, or, when the day's chain lacks it, from Black-76 at that day's ATM IV (else the entry IV, else intrinsic) and is then "modelled". Equity is realised P&L over closed trades per recorded day; stats are count, win rate, average, median, best, worst, max drawdown and profit factor; coverage names the first and last day, the entries, the days skipped (no expiry far enough out, ladder too short), the open and the modelled trades. No fees, no slippage, and the tab says so. (4) `GET /v1/backtest?asset&template&lots&minDte&from&to&venue` behind the session, every plan (GAPS #93), money to cents, `private, max-age=300`, 503 until a day is recorded, 400 for an unknown template or a reversed range; the folded days are memoised in process per venue and underlying and revalidated by a count (the table changes once a day, the tab asks once per template), `from` bounds the days read and `to` only the entries, so a trade entered inside the range still settles after it. (5) The Backtest tab in the analysis pane (also from the palette): template by category, lots, minimum days to expiry, 7D / 30D / 90D / 1Y range, the coverage line first, five tiles, the equity curve on the analytics SVG chart, the trades newest first with legs, cost, exit and P&L, "open · marked <day>" and "modelled" where they apply, and an honest empty state before the first recorded day.

**Consequences.** The evidence base grows one day per day; a claim about a template is only as long as the coverage line, which is why the line comes first and why the copy stays "ready-made structures". Replay of an expiry's chain (B9b) can use the same table for daily steps and the 5-minute marks for the last week. Rejected: computing in the browser from a shipped history (megabytes per run), extending the 5-minute mark retention (1.8 M rows a week), and modelling pre-record days from ATM IV alone (no strike ladder, no skew: it would read as history and is not).

## ADR-078 · A typed LIVE interlock on every live entry, and a TOTP second factor through better-auth's twoFactor plugin (2026-09-12)
**Context.** Roadmap item 28 / GAPS #73: an account that places real orders confirmed them with one plain click (`trade-now`, `batch-go`, the card's one-click retry, the adjust hold button), no route read a confirmation, and better-auth ran with email OTP, passkeys and optional Google only, so a stolen password or a signed-in laptop was enough to trade. Better-auth 1.7.3 ships a `twoFactor` plugin (server `better-auth/plugins/two-factor`, client `twoFactorClient`) that needs a `two_factors` table, a `users.two_factor_enabled` flag and nothing installed; its sign-in hook covers only the password, username and phone paths, so the email-OTP and social paths would have bypassed the second factor. The order bodies are strict objects.
**Decision.** (1) Typed LIVE is a server-side interlock on live ENTRIES, mirrored in the client: `LivePlaceBody`, `LiveBatchBody`, `AdjustBody`, `AddLegsBody` gain an optional `confirm` (trimmed, up to 16 chars) and retry gets a body `LiveRetryBody { confirm? }`; `requireLiveConfirm` in `routes/live-exec.ts` answers 400 "Type LIVE to confirm a real order" unless `isLiveConfirm(word)` (case-insensitive, trimmed) holds, on place (after the idempotency replay, before status and entitlement), batch (first), retry (before the status check), a live adjustment that carries entry orders (`adds`) and add-legs on a live strategy. Exits, square-offs and partial exits stay one click: they reduce risk (ADR-074's line). Paper never asks. The client sends the word as typed, never a constant, so a client that skips the field is refused too. (2) One `TypedConfirm` field ("Type LIVE to place / retry / adjust", mono, upper-cased as typed, Enter submits when the word is in) under the red block of `TradePreviewDialog` (live), `BatchLiveDialog`, `AdjustConfirmDialog` (live with adds; the hold button stays and is disabled until the word) and a new `RetryDialog` that names the refused legs; the destructive button is disabled, not hidden; with the Mindful pause the countdown still replaces the button and the field is typeable during the pause. (3) TOTP through the `twoFactor` plugin (issuer "HapieCoin", `skipVerificationOnEnable: false`, so nothing changes until the first code): drizzle `two_factors` + `users.two_factor_enabled` (migration), `authOptionsPublic.totp: true`, `/v1/me` gains `twoFactorEnabled`. With 2FA on, only password + code signs in: a `hooks.before` refuses `/sign-in/email-otp` and a sign-in `send-verification-otp` for such an account with 403 `TWO_FACTOR_REQUIRED` ("This account uses an authenticator app: sign in with your password and the code"), and a `session.create.before` database hook refuses a session for a 2FA account from any path other than `/sign-in/email` and the `/two-factor/verify-*` endpoints (so Google and passkey sessions cannot skip the code either). The verify endpoints refuse `trustDevice` (the plugin would otherwise honour it from any caller and skip the code for 30 days), and the plugin's 3-per-10 s rule is widened to 10 per minute on the two verify paths so a mistyped first code never meets a 429 (the plugin still counts failed codes and locks the account). A Google sign-in on a 2FA account returns to `/auth` with the reason in the URL (`errorCallbackURL`), which the login form shows. (4) Web: `twoFactorClient()`; `LoginForm` branches on `twoFactorRedirect` to a new `AuthTab` "totp" (6-digit `OtpInput`, a backup-code alternative, `trustDevice: false`); a `SecurityDialog` (DialogKind "security", the settings menu row reads "2FA on / off", palette "Open Security") turns it on in three acts (password → the key in groups of four with the otpauth link, no QR image → the first code) and then shows the backup codes once; turning it off asks for the password. The mock API mirrors the flow with one fixed test code (654321) and the same refusals.
**Consequences.** No client and no script places a live entry silently: the word travels with the order and the API decides. A trader who turns 2FA on signs in with the password and a code from the app, or a backup code once; email codes and Google are refused for that account with the reason spelled out (the plugin's `twoFactorRedirect` never fires on those paths, so refusing is the only honest answer). Not built (GAPS #94): a QR image (needs a library; the key and the otpauth link cover manual entry and same-device apps), a trusted-device option (refused server-side), admin visibility of 2FA state, a second factor on the API-key routes, the passkey UI (GAPS #12), and a server-side check that the word came from a human (it is an interlock, not proof). Tests: schema `strategies.test.ts` (HC-TR-186 word rule), api `live.test.ts` HC-TR-186 (place / batch / retry / live adjust add / live add-legs 400 without the word, trim and paper add 200), `auth.test.ts` HC-PB-068 / HC-SH-129 (enable → first code → `/v1/me` flag; password sign-in → redirect → code → session while the email-OTP paths answer 403; disable), web `trading-live.test.tsx` HC-TR-186 (button disabled until LIVE, batch, the retry dialog), `AuthForms.test.tsx` HC-PB-068, `dialogs.test.tsx` HC-SH-129, `shell.test.tsx` (palette row); e2e `analyse.spec.ts` (the word typed before every live click), `auth.spec.ts` HC-PB-068, `settings.spec.ts` HC-SH-129 (first runs are the PR's CI).

## ADR-079 · Replay of an expiry's chain: recorded instants only, daily over the end-of-day history and every five minutes over the last week, the Builder's legs marked from what was recorded (2026-09-12)

**Context.** Roadmap item 9, part b (research §3 takeaway 5: Opstra's simulator replays a past session in 5-minute steps). After ADR-077 the venue's chain is recorded once a day for 400 days (`chain_eod`) and every five minutes for seven days (`instrument_marks`, ADR-056), so a replay can show what the venue published at those instants and nothing else.

**Decision.** (1) Three session-guarded routes, read-only over the snapshot tables and bound by their indexes: `GET /v1/replay/expiries` (every expiry with a recorded chain, the end-of-day days held and whether the venue still lists it, from the latest pass's symbols), `GET /v1/replay/steps` (the daily instants that carry the expiry and, through one of its symbols, every 5-minute pass of the last week with the spot of the same pass) and `GET /v1/replay/chain` (the ladder at an instant: the end-of-day rows stamped then, else the marks of that pass parsed through the venue codec; 404 when nothing was recorded then). 503 while nothing is recorded for the underlying. (2) A Replay tab in the analysis pane (also from the palette): expiry (the first still listed by default; a past expiry the venue no longer lists reads "settled", a future one "delisted"), Daily / 5-min resolution with the step counts (the other resolution takes over when the chosen one has no instant for the expiry), a slider with previous / next / play (one step per 400 ms, from the start again when at the end; the position is kept per expiry and resolution so a refetch never moves it), the readout (instant, spot, "recorded end of day" or "recorded 5-minute pass", n of N) and the ladder with the ATM row (the Builder's rule) marked; while the next instant loads the previous ladder stays on screen dimmed and the readout waits, so a figure never sits under the wrong instant. The 5-minute instants of an expiry are read through every symbol the latest pass lists for it (a strike listed late must not shorten the window), the latest pass itself through the IV rows, and the spot of each pass through the front-expiry IV row. When the Builder holds legs on that expiry, their side is shown on their strike row and the readout gives the position's mark-to-market versus entry from the recorded marks alone; a leg without a recorded mark at that instant makes the readout say so instead of a number. (3) Nothing is modelled and nothing is a fill: the copy says "marks as the venue published them", never "replayed live".

**Consequences.** Replay reaches seven days at 5-minute resolution and the whole end-of-day history daily; a symbol the venue delisted before its expiry (or that was never listed at a pass) simply has no row at that instant. The mock API serves synthetic instants from the recorded instrument fixture so the tab is tested without the snapshot tables. Rejected: interpolating between instants (it would invent marks), replaying from the 5-minute stream beyond its retention (the rows are gone), and a per-strike IV surface over time (B9c if ever; the tab shows the recorded mark IV per row).

## ADR-081 · Error tracking through the Sentry envelope protocol without an SDK, API metrics in Prometheus text, browser errors relayed through the API (2026-09-12)
**Context.** Roadmap item 27 / GAPS #72: the API logged JSON through pino and answered `/healthz`, only the gateway served Prometheus metrics, nothing caught a failure in the browser, and docs/deploy.md §6 left the error tracker as an open decision. Adding a vendor SDK meant three new dependencies with auto-instrumentation weight, before the vendor was even chosen; an `errors` table nobody watches is not tracking. Every tracker worth choosing (Sentry, self-hosted GlitchTip, Bugsink) accepts the same wire format: one DSN, `POST {base}/api/{project}/envelope/`, an `X-Sentry-Auth: Sentry sentry_version=7, sentry_client=…, sentry_key=…` header, an envelope of a header line, an item header and the event JSON, frames oldest-first (develop.sentry.dev, envelopes and the event schema, read on 12 Sep 2026).
**Decision.** (1) One in-house error sink per process (`apps/api/src/error-sink.ts`, the same file in `apps/gateway/src/error-sink.ts`): `createErrorSink({ dsn: ERROR_SINK_DSN, environment, release: RELEASE })` builds and posts envelopes with `fetch`, no SDK; every tag, extra and message is redacted by the logger's secret-key rule, a request carries only method, scrubbed path and user agent (never a body, cookie or authorization header), a user only its id; sends are fire-and-forget with a 3 s timeout, capped at 60 events a minute (the rest counted as dropped), flushed on shutdown; without a DSN every call is a no-op, so tests, a laptop and CI need nothing. (2) The capture seam is the log: the API's pino gets a `hooks.logMethod` that hands every error- and fatal-level record (child bindings included, so the request id travels) to the sink, and the gateway's logger does the same for its error level, so 500s (`onError` now logs the Error itself with method, scrubbed path, route pattern, request id and user id), job failures, feed faults and the process-level `unhandledRejection` / `uncaughtException` handlers all reach the tracker through the one line they already log, and nothing is captured twice; both process handlers flush the sink and then end the process, so Node's semantics stay (a half-done job tick never runs on). Two things the seam's callers could leak are cut at the sink: a drizzle query error quotes its bound values after `params:` (an OTP, a session token), so the message is cut there and pino redacts `err.params` / `err.query`; personal-data keys in log fields (`to`, `email`, `name`, `phone`, `mobile`, `user`) are dropped before `extra`. (3) `GET /metrics` on the API renders Prometheus text by hand like the gateway's: `hapiecoin_api_requests_total{method,route,status}`, a `hapiecoin_api_request_duration_seconds` histogram per route, `hapiecoin_api_errors_total{kind}`, the sink's sent / dropped / failed counts, jobs active, uptime and process memory; the route label is Hono's matched pattern (`/v1/strategies/:id`; `(other)` when nothing matched), never the raw path, so a URL scan cannot grow the series; `/metrics` and `/healthz` are not counted; `METRICS_TOKEN` guards the route with a bearer like the gateway (GAPS #30, compared in constant time); the gateway's `/metrics` gains the same sink-count block. (4) Browser errors go through the API: `POST /v1/client-errors` (no session, 5 reports a minute per address, a strict body of message, name, stack ≤ 4 000, path, kind) relays a `javascript` event tagged `browser:<kind>` (the body's `release` becomes the event's release, never a tag: Sentry reserves that key), so no DSN ships to the browser and the server scrubs; the web installs `window` error and unhandled-rejection listeners once (one report per message per minute, a failed report is swallowed), and `app/error.tsx` / `global-error.tsx` show "Something broke on our side. It has been reported." with the tracker's reference, Try again and Reload, and say plainly that a page error cannot change strategies or orders on the exchange.
**Consequences.** The vendor choice in docs/deploy.md is now an env value, not a code change: any Sentry-protocol server works from `ERROR_SINK_DSN`, and events carry environment, release, server name, route, request id and user id. Ops reads one `/metrics` shape from both apps. The API's unhandled-error log line now carries the stack (pino's `err` serializer) where it carried name and message before. Not built (GAPS #97): better-auth's own failures (answered inside `auth.handler` by the library's console logger, not through pino), tracing spans and timings, source maps for the browser frames (minified names), sampling, a shared server package for the duplicated sink file, alert rules and uptime pings (deploy-time), the web build's own release tag (browser events carry the API's), and a second factor or session on the client-error route (rate limit only). Tests: api `error-sink.test.ts` (DSN parsing, stack frames, redaction agreeing with the logger, envelope shape, cap, timeout and failures, the log-record mapping), `metrics.test.ts`, `observability.test.ts` (the pino hook, `/metrics` with and without the token, a 500 reaching the sink), `routes/client-errors.test.ts`; gateway `error-sink.test.ts`, `log.test.ts`, `config.test.ts`, `app.test.ts` (an error log reaching the injected sink, flush on stop, the off sink); web `lib/errors/report.test.ts`, `app/error.test.tsx`. No e2e: a deliberate crash is not a scriptable path; the rows read unit (api + gateway + web).
